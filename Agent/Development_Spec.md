## 1. 产品目标与边界

### 1.1 产品定位

VoyageDeck AI 是一款面向“单人借助 AI 管理跨境业务”场景的可视化指挥台。它用六个岗位型 AI Agent 演示一个完整业务闭环：

`选品 -> 上架 -> 内容制作 -> 广告投放 -> 客服 -> 履约`

用户应能从一个界面理解：当前谁在干活、执行到哪一步、哪一步需要人工批准、产生了什么文案或方案、失败原因是什么、业务数据如何变化。

### 1.2 本期视频必须能展示的故事

打开网页后，看到正在运行的“出海星舰”；点击“新建出海任务”，从模拟选品库挑选产品并设定目标市场；点击“启动演示”；中央六智能体流程依次点亮；右侧岗位卡片和下方实时日志同步更新；系统在关键节点展示可审核的产物；出现不满足毛利门槛的产品时自动淘汰；最终显示订单模拟、GMV、成本、利润和投放回报的**计算依据**；还能暂停、继续、重置、复盘。

### 1.3 交付范围（P0：本期必须完成）

- 可公开访问的访客演示 UI，访客之间的演示互不干扰；无 Key 就能体验。
- 六智能体工作流及完整任务状态机；模拟运行不是单纯的动画序列。
- 可配置的演示场景、模拟产品、订单、成本、任务日志和 KPI 计算。
- 管理员模式：查看持久化任务、审阅 AI 产物、配置 Provider（敏感信息只存服务端）、运行真实文本推理。
- 可配置 Mock Provider；至少留出一个 OpenAI-compatible HTTP API 适配层，用于 DeepSeek、豆包或其他合规可用服务；接入是否成功取决于用户提供的有效 Key 与接口配置。
- 单元测试、关键端到端测试、README、部署文件、API 文档、演示脚本。

### 1.4 暂不实现（P1 或后续）

- 不接入真实 Shopify、Amazon、TikTok Shop、1688 等业务账户。
- 不创建真实商品，不下真实广告订单，不扣费，不操作物流，不自动回复真实买家。
- 不做多租户付费 SaaS、分销结算、支付系统或真实财务报表。
- 不部署真实大模型权重，不承诺一个普通 VPS 能运行大参数模型。
- 不将“AI 已生成建议”等同于“业务已执行成功”。

- 风格：Cyber Command Center / Mission Control / Dark AI Operations Console。
- 气质：精密、克制、专业、未来感；避免廉价荧光色堆砌、过度毛玻璃、营销页式大留白。

- 动效：数字平滑递增、心跳指示灯、任务进度、光点沿流程线移动、日志逐条出现、状态切换微动效；遵守 `prefers-reduced-motion`，不可造成明显掉帧。
- 细节：卡片统一圆角、细描边、内阴影与渐变层次；悬浮与聚焦有明确响应；加载、空态、失败态均经过设计。

1. **顶栏 / 舰桥状态栏**：原创 VoyageDeck 图标、项目名称、当前模式（演示/真实推理）、目标市场、运行状态、系统时间、开始/暂停按钮、设置/管理入口。
2. **任务总览区**：核心数值卡：GMV、订单数、模拟广告消耗、ROAS、预计毛利、工作中的 Agent 数；数字需附口径或 Tooltip；演示模式始终可见“模拟数据”标识。

4. **左中业务决策区**：当前候选商品（虚构名称、SKU、成本、定价、毛利率、淘汰原因）、阶段决策面板、当前任务概览。
5. **中下实时终端区**：`ops.log` 风格实时日志、时间戳、角色色、级别标签、任务 ID、事件内容；支持筛选、滚动、暂停自动滚动、查看历史。
6. **底部业绩趋势 / 时间轴**：GMV 与成本变化迷你图、任务里程碑、订单模拟列表；趋势随模拟事件真实变化。

8. **任务交互区**：新建任务、选择情景、启动、暂停、恢复、单步执行、重置、查看复盘；确认弹窗须准确描述影响。

建议把布局做成“主舱 + 右侧岗位塔”而不是均匀的六等分普通仪表盘。中央流程与实时日志是视觉主角。

## 3. 六智能体功能要求

每个智能体必须拥有：独立 Agent ID、名称、状态、输入契约、输出结构、执行开始/结束时间、任务关联、失败原因、重试次数、日志事件、可读的用户产物。真实 AI 推理模式不得让模型任意执行系统命令。

### Agent 1：选品官（Scout）

- 输入：目标市场、类目、预算、利润门槛、候选商品清单。
- 处理：评分候选产品（需求、毛利、竞争程度、合规风险、供应可靠性）；利润不足或风险过高的商品淘汰并说明原因。
- 输出：候选评分、建议商品、估算成本售价、毛利率、选/淘汰理由。
- 模拟场景必须包括至少一个成功候选和一个因毛利不足被淘汰候选。

### Agent 2：上架官（Lister）

- 输入：获批商品、市场、目标语言、卖点与合规提示。
- 处理：生成商品标题、五点描述、SEO 关键词、SKU 草稿、定价建议。
- 输出：结构化上架草稿，状态为 `draft`，**不得标记为已在真实平台上架**。
- 人工审核可批准或退回草稿，审批动作留痕。

### Agent 3：内容官（Creator）

- 输入：上架草稿、用户画像、渠道、语言、产品卖点。
- 处理：生成广告短视频脚本、社媒帖文、标题和创意 brief。
- 输出：可复制的结构化文案及短视频分镜（文本即可，不强求视频渲染）。
- 不得自行下载侵权素材或套用用户未提供的品牌资产。

### Agent 4：投流官（Ads）

- 输入：内容素材、虚构广告预算、预计转化率、成本和目标 ROAS。
- 处理：生成投放计划、渠道建议、投放预算分配、KPI 风险提示。
- 输出：`模拟投放计划` 或 `待人工批准的投放建议`；不接真实广告平台。
- 预算不可为负、消耗不能超模拟预算；展示 ROAS 必须来自模拟归因收入/模拟广告成本。

### Agent 5：客服官（Service）

- 输入：模拟客户咨询、订单上下文、售后规则。
- 处理：分类咨询、草拟回复、标记高风险和需人工处理项。
- 输出：待审核客服回复，或在**隔离的模拟对话**中完成回复；不得给真实用户发送消息。
- 包含英语客服示例；必要时提供中英对照。

### Agent 6：履约官（Fulfillment）

- 输入：模拟订单、SKU 库存、履约规则、售后状态。
- 处理：模拟订单校验、库存占用、模拟发货、失败/退款情况。
- 输出：模拟履约事件、订单状态与成本记录；不能生成冒充真实承运商的追踪信息。

## 4. 工作流引擎与状态机

### 4.1 工作流状态

工作流：`draft -> ready -> running -> paused / awaiting_approval -> completed / failed / canceled`。

任务：`pending -> queued -> running -> awaiting_approval -> succeeded / failed / skipped / canceled`。

转换必须经后端或统一状态管理校验，不允许前端任意更改结果来跳过审批；前端与持久化事件要一致。暂停时不能继续启动新任务，恢复后不重复完成已执行任务。

### 4.2 标准串行演示流

1. 用户从虚构商品样例中选择目标市场（例如美国或欧洲的模拟市场）与类目。
2. Scout 筛选三条候选商品；拒绝其中一条毛利不足候选，选择一条用于演示。
3. Lister 生成商品草稿；可进入人工确认，访客模式可用“批准模拟草稿”继续。
4. Creator 生成短视频脚本和社媒文案。
5. Ads 生成虚拟投放方案，投放预算必须确认；访客模式操作的是模拟预算。
6. Service 接收三条虚构客户提问并生成建议回复。
7. Fulfillment 模拟两个订单的成功、失败或退款事件，所有事件归属对应订单。
8. 工作流终止后自动输出可下载或复制的复盘摘要：每步输入/输出、耗时、KPI 来源、失败/风险、人工审批动作。

至少提供三套可复现情景：

- 场景 A：标准成功闭环。
- 场景 B：低毛利淘汰后切换备选商品。
- 场景 C：某岗位超时或失败、重试后进入人工处理或失败态。

### 4.3 必须有的用户操作

- 新建、启动、暂停、恢复、单步前进、重置**个人演示沙盒**。
- 点击某一岗位查看输入、结果、耗时和日志。
- 审阅 / 驳回模拟草稿或预算建议，并展示审批记录。
- 切换演示情景；切换场景须重置或明确隔离状态，不混用旧任务指标。
- 筛选事件级别、角色、任务；可复制复盘和典型 AI 产物。
- 真实 Provider 配置无效时，显示明确错误，不得静默伪造成功。

### 4.4 健壮性与并发

- 任务有稳定 UUID、工作流 ID、事件序号、创建和更新时间。
- 持久化模式采用幂等事件处理，防止重复点击导致重复计数和重复扣模拟预算。
- 重试上限默认 2 次，失败后明确可见；合理设置超时与取消逻辑。
- 后端重启后可以查询历史状态；运行中未完成任务需按可解释策略恢复或标记为 interrupted，不得假装成功。
- 单机演示优先限制并发与队列长度，避免占满低内存 VPS。

## 5. 数据模型与 KPI 真实性

### 5.1 最小实体

建议实现 `agent`, `workflow_run`, `task`, `task_attempt`, `agent_output`, `approval`, `event_log`, `product_candidate`, `listing_draft`, `content_draft`, `ad_plan`, `order`, `order_event`, `metric_snapshot`, `provider_config`。具体表结构可按实现简化，但关键业务事实不可仅保存在前端数组里。

- 业务事实与 UI 展示分离。所有事件可追溯到任务与业务记录。
- 模拟数据使用固定随机种子或内置情景数据，测试可复现。
- 数据带 `data_source` / `mode` 字段，例如 `demo_simulated`、`ai_generated_draft`、`external_verified`；P0 不会产生 `external_verified` 的真实外部交易事实。
- 时间戳服务端用 UTC 存储，前端按浏览器时区展示。

### 5.2 指标定义

- `GMV`：模拟已创建且符合定义的订单商品成交总额；默认不计入已取消订单，退款单另列出退款金额，不与净营收混淆。
- `净销售额`：计入业务规则下的成交收入减退款；不要直接叫“利润”。
- `商品毛利`：净销售额减对应商品采购成本；`毛利率 = 商品毛利 / 净销售额`（分母为 0 显示 N/A）。
- `广告 ROAS = 模拟广告归因销售额 / 模拟广告支出`；0 支出显示 N/A，而不是 0 或无限大。
- `估算贡献利润 = 净销售额 - 商品采购成本 - 订单物流成本 - 平台费用 - 模拟广告支出 - 其他已列出的可变费用`；明确这不是经审计净利润。
- 金额统一显示货币单位与币种。默认 demo 用 USD，必要时让用户切换展示语言而非随意混币。
- 数值卡不得使用与订单事件互不关联的任意跳动随机数。

### 5.3 示例数据

优先使用虚构产品（如 `NomadPack Travel Organizer` / `旅行收纳包`），并在示例说明里标明“虚构商品”。至少有：三件模拟候选、两条模拟订单、三条客服咨询、一个投流计划、一个成功场景、一个失败/淘汰场景。

## 6. 推荐技术架构

Codex 可根据现有环境作有理由的微调，但不得为了框架炫技引入大规模基础设施。优先考虑“可维护、资源轻、接口清晰、在已有 VPS 旁边安全运行”。

### 6.1 建议技术栈

- 前端：React + TypeScript + Vite；Tailwind CSS 或等效样式体系；适量使用 React Flow（或自建 SVG 流程图）、Lucide、轻量图表与 Motion 动效。
- 后端：Python + FastAPI，Pydantic / SQLAlchemy，提供 OpenAPI 文档。
- 数据库：开发及单实例 MVP 可用 SQLite + WAL + 正确事务；通过迁移方案保留升级 PostgreSQL 的可能；不强制上线 Postgres/Redis。
- 实时：优先 Server-Sent Events（SSE）推送任务事件；重连使用事件序号恢复；连接失败提供轮询降级。
- Agent 层：Provider Adapter 接口 + Mock Provider + OpenAI-compatible Adapter。所有外部 API 在服务端调用，支持配置 endpoint、model、超时、token 上限及限速。
- 测试：前端单元测试 + Playwright E2E，后端 pytest，接口集成测试。
- 本地开发：一条命令启动前后端，明确 Windows PowerShell 说明；生产使用资源受限的独立 Docker Compose 项目。

### 6.3 API 最低建议

- `GET /api/health`：存活状态，不泄露生产配置。
- `GET /api/agents`：角色配置及状态。
- `GET /api/workflows`、`GET /api/workflows/{id}`：列表与详情（管理员）。
- `POST /api/workflows`、`POST /api/workflows/{id}/start`、`/pause`、`/resume`、`/cancel`：权限控制。
- `POST /api/workflows/{id}/approve`：审批动作与审计记录。
- `GET /api/workflows/{id}/events`：分页历史事件。
- `GET /api/events/stream`：SSE，支持重连 / 事件序号。
- `GET /api/metrics`、`GET /api/orders`、`GET /api/outputs/{id}`：后端事实与汇总。
- `GET/PUT /api/settings/provider`：管理员配置；返回值必须隐藏 Key。

访客模式可以完全在前端沙盒中运行，不必暴露写接口给匿名访客；如果提供服务端访客写接口，必须实现每会话隔离、资源上限、过期清理与限流。

### 6.4 真实模型与模拟模式必须隔离

**Demo Sandbox：** 默认开启；浏览器会话级隔离；固定数据集；零模型调用费；可重置与重放；任何“GMV、订单、发货、广告投放”全部标“模拟”。

**Admin AI Mode：** 登录管理端后才可用；用户配置有效 Provider；可以对选品理由、商品描述、内容脚本、投流建议、客服草稿、履约说明等文本任务进行真实模型调用；模型输出经过结构化校验；不得将 AI 生成的文案误标记为真实平台执行结果。

不要在前端打包任何真实 API Key；不要将 Provider Key 存入浏览器 LocalStorage、URL 参数、日志、截图或公开配置。若持久化凭据无法安全实现，P0 优先采用后端环境变量配置，并仅在管理页显示 Key 是否已设置。

## 7. 访问控制、安全与合规

- 公共访问首页默认进入隔离的交互式 Demo Sandbox；首页清晰显示“模拟数据 / Demo Mode”。

- 使用依赖锁文件；运行依赖漏洞/密钥扫描（可用环境工具）并说明发现及处理。
- 审阅和日志不能包含明文 Key、认证 token 或真实个人信息。
- README 不可以宣称存在尚未实现的真实平台集成。
